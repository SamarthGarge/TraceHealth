2.2 Project Description
Project Description

What TraceHealth does and why it matters

TraceHealth is a full-stack, explainable AI-powered health risk screening platform that allows users to assess their risk for four major diseases — Diabetes, Heart Disease, Tuberculosis, and Lung Cancer — using validated machine learning models. Unlike traditional "black-box" health prediction tools, TraceHealth pairs every prediction with SHAP (SHapley Additive exPlanations)-based reasoning, enabling users to understand exactly which health parameters drove their risk score and by how much.

The platform employs three distinct ML algorithms — Logistic Regression, Random Forest, and XGBoost — for each disease, running all three simultaneously and presenting a side-by-side comparison. An ensemble average provides a balanced overall risk level (Low, Moderate, or High), while individual model results let medically literate users or practitioners examine algorithmic consensus or disagreement.

On the backend, TraceHealth is built with FastAPI (Python), serving a REST API with JWT-based authentication, role-based access control (user/admin), Google OAuth integration, and password reset via Gmail SMTP. The frontend is a modern single-page application built with React 18, Vite, React Router, Zustand for state management, and GSAP for premium animations. Data is persisted in MongoDB Atlas using Motor (async driver), with GridFS for secure medical file uploads.

Key features include: prediction history with full SHAP detail, a rule-based symptom checker triage wizard, secure medical file upload and AI-powered report analysis, data export in CSV/JSON/PDF formats, an admin dashboard with platform-wide statistics, and a responsive editorial design optimized for both desktop and mobile. The platform is designed for free-tier deployment on Vercel (frontend) and Render (backend), making it accessible to students, researchers, and low-resource clinics without any hosting costs.

2.3 Existing Systems
Existing System Study

Three similar systems and their limitations

An analysis of existing health prediction tools and the manual working environment.

System 1

ADA Health Symptom Checker

Conversational AI-based symptom assessment. Covers many conditions but provides no ML model transparency, no SHAP explanations, and no prediction history. Users cannot compare algorithms or export results.

System 2

WebMD Symptom Checker

Rule-based symptom matching tool. Provides possible conditions but offers no quantitative risk scoring, no ML predictions, no explainability, and no personalized history tracking or data export capabilities.

System 3

Kaggle ML Notebooks

Individual disease prediction notebooks (Diabetes, Heart) exist as isolated experiments. They lack a unified UI, authentication, history persistence, SHAP integration, and are not deployed as usable web applications.

Manual Working Environment

In the manual process, patients visit multiple specialist clinics for each disease screening. Lab reports are collected on paper, risk assessment relies entirely on physician intuition, results are siloed across departments, and there is no centralized platform for patients to track their health risk trends over time. This fragmented approach is time-consuming, expensive, and inaccessible to populations in remote areas.

2.4 Problem Statements
Problem Statements

Core problems this system solves

Chronic and infectious diseases share a common gap between the data that predicts them and the tools people can actually use.

Siloed screening. Diabetes, heart disease, TB, and lung cancer risk are assessed by separate, disconnected tools — no single, consistent screening experience exists for multiple diseases.

Black-box predictions. Most ML risk scores arrive with no reasoning attached, which limits trust and makes it impossible for users or doctors to understand why a result was high or low.

No historical tracking. Users cannot track how their health risk evolves over time, compare previous screenings, or detect trends in their risk factors across multiple assessments.

Resource-heavy deployment. Production-grade health apps require expensive cloud infrastructure, putting usable tools out of reach for students, researchers, and low-resource clinics.

No data portability. Users cannot export their health screening data in standard formats (CSV, JSON, PDF) to share with healthcare providers or maintain personal health records.

Limited accessibility. Existing tools are often desktop-only, require technical ML knowledge, or lack responsive design for mobile access in field healthcare settings.

2.5 Need for New System
Need for New System

Why a new system is necessary

Strong technical and social reasons to build TraceHealth from the ground up.

🏥 Unified Multi-Disease Platform

No existing free tool provides a single interface to screen for Diabetes, Heart Disease, TB, and Lung Cancer simultaneously with consistent UX and methodology.

🔍 Explainability Gap

SHAP-based per-prediction explanations are virtually absent in consumer health tools. Users deserve to know why their risk is what it is, not just the number.

📊 Multi-Model Transparency

Running 3 different algorithms (LR, RF, XGBoost) and showing results side-by-side gives users and clinicians unprecedented model transparency and consensus validation.

💰 Zero-Cost Deployment

Built specifically for free-tier hosting (Vercel + Render + MongoDB Atlas M0), making it deployable by students and NGOs without any infrastructure budget.

📱 Mobile-First Design

Fully responsive editorial design works on mobile phones in field healthcare settings, unlike desktop-only research notebooks and Streamlit prototypes.

🔒 Privacy by Design

GDPR-style data consent, httpOnly JWT cookies, role-based access, and ownership-enforced data isolation — a level of security absent in prototype health tools.

Proposed System

Modules, features, and functionalities

11 major modules comprising 27+ screens and 40+ API endpoints.

Authentication

Email/password signup & login, Google OAuth, JWT access + refresh tokens (httpOnly cookies), password reset via Gmail SMTP, admin login.

M2

Disease Prediction

Run predictions for 4 diseases using 3 ML models simultaneously. Input validation, feature preprocessing, ensemble averaging, risk classification.

M3

SHAP Explainability

Per-prediction SHAP feature attribution for every model. Top contributors shown as interactive bar charts with direction indicators.

M4

Prediction History

Paginated history with disease filter. Full detail view with SHAP breakdown. Delete individual predictions. Ownership-enforced access.

M5

Symptom Checker

Rule-based triage wizard with weighted symptom scoring. Produces referral suggestions per disease to guide which prediction to run.

M6

File Upload & Analysis

Secure GridFS upload (PDF, PNG, JPEG, CSV). Magic-byte validation, 10MB limit. AI-powered report analysis for uploaded medical documents.

M7

Data Export

Export predictions as CSV, JSON, or professional PDF reports. Date range filtering, per-prediction or bulk export. WeasyPrint PDF generation.

M8

Admin Dashboard

Platform-wide stats (user count, prediction count, disease distribution). Browse all users, view user details, recent predictions.

M9

User Management

Profile editing, account deletion, data consent management. Role-based access control (user/admin). Secure password hashing (bcrypt).

M10

Health Resources

Curated disease-wise links to WHO, CDC, AHA, and other authoritative sources. Tabbed interface with resource type badges.

M11

Model Transparency

About Models page showing training methodology, accuracy metrics, dataset sources, and feature lists for all 12 trained models.

3.1 Feasibility Study
Requirement Analysis

Feasibility Study

🔧 Technical Feasibility

All technologies used (React, FastAPI, MongoDB, scikit-learn, XGBoost, SHAP) are mature, open-source, and well-documented. The team has working proficiency in Python and JavaScript. Pre-trained models are serialized to lightweight joblib files (~12MB total). The full-stack architecture has been validated locally with all 40+ API endpoints functional and tested.

💰 Economic Feasibility

The entire project runs on free tiers: Vercel (frontend CDN), Render (backend hosting), MongoDB Atlas M0 (512MB cloud DB), and Gmail SMTP (password reset emails). Total development cost is $0. No paid licenses, no proprietary software. All ML training datasets are publicly available from UCI/Kaggle repositories.

⚙️ Operational Feasibility

The system requires no training to operate — users simply enter health parameters and receive results. The editorial UI design with clear visual hierarchy ensures usability for non-technical users. Auto-deploy from GitHub means zero-downtime updates. Admin dashboard provides operational monitoring without server access.

🌍 Social Feasibility

TraceHealth promotes health awareness and early disease detection. It is designed to be socially inclusive: free access, responsive for mobile (reaching rural populations), multilingual-ready architecture, and GDPR-style consent ensuring ethical data handling. SHAP explanations empower users rather than creating dependency on opaque AI.

3.3 System Modules
Module Breakdown

Detailed module descriptions

🔐 Authentication Module

Handles signup (name, email, password, consent), login (email/password + Google OAuth), logout, JWT token management (access + refresh), password reset via email (Gmail SMTP), and admin login with role elevation.

🧠 Prediction Engine

Core ML pipeline: accepts disease key + feature dict, validates inputs against model metadata, preprocesses (scales) features, runs 3 models (LR, RF, XGB), computes SHAP attributions, calculates ensemble average, and classifies risk level. Saves to history if user is authenticated and consented.

📋 Symptom Checker

Rule-based triage wizard. User answers yes/no symptom questions. System applies weighted scoring per disease, normalizes to 0–100, and returns referral suggestions ranked by relevance with actionable reasons.

📁 File Upload & Analysis

Secure medical file upload via GridFS (PDF, PNG, JPEG, CSV). Magic-byte MIME validation, 10MB limit, filename sanitization. AI-powered analysis extracts health data from uploaded reports for interpretation.

📊 Export & Reporting

Exports prediction history in CSV, JSON, or professional PDF format. Supports date range filtering, disease filtering, and single-prediction export. PDF generated with WeasyPrint using HTML templates.

🛡️ Admin Dashboard

Platform-wide stats: total users, total predictions, predictions by disease, recent activity. Paginated user list with search. Individual user detail view. Recent predictions feed across all users.

3.4 Process Model
Development Strategy

Agile (Scrum) Process Model

TraceHealth follows the Agile methodology with Scrum-based sprints. This is ideal because the project evolved iteratively — from a Streamlit prototype to a full-stack React + FastAPI application.

Why Agile Scrum?

  • Iterative delivery: Each phase (data → model → API → UI) delivered a working increment.
  • Changing requirements: The project evolved from 4 slides (initial proposal) to 11 modules with 27+ screens.
  • Continuous feedback: Browser-based testing after each sprint enabled rapid UI/UX iteration.
  • Risk management: ML model accuracy was validated early (Phase 2) before building the full UI.
  • Parallel work streams: Frontend and backend could be developed concurrently with API contracts.
